# 商机验证中心维护设计

## 目的

商机不是一次 AI 结论，而是一条可以长期维护的业务记录。它回答三个相互独立的问题：

1. 这个地区是否存在持续需求；
2. 是否值得开发这一类买家；
3. 是否值得寻找并组织对应货源。

系统把“项目范围”和“可复用资产”分开：`买家画像 + 地区 + 采购场景 + 销售渠道` 定义唯一活动项目，项目内可选择多条产品矩阵；`地区 + 产品家族` 定义共享产品档案。单品、供应商报价、客户线索和历史销售数据持续增加，但不反向覆盖画像、赛道或产品家族主数据。

## 持久化模型

| 表 | 用途 | 更新规则 |
| --- | --- | --- |
| `opportunity_programs` | 验证项目范围、双人分工、当前轮次、复核日期和作废信息 | 同一项目范围只允许一个活动项目；作废不删除 |
| `opportunity_rounds` / `opportunity_round_families` | 每轮目标、产品矩阵快照、去留和决策 | 轮次结束后保留历史，不覆盖 |
| `opportunity_dossiers` | `地区 + 产品家族` 的共享调研档案 | 跨项目复用；独立维护版本与复核时间 |
| `opportunity_cases` | 商机主档、负责人、阶段、复核日期和下一步行动 | 可更新；每次更新增加版本号并写入变更日志 |
| `opportunity_assessments` | 每轮九项验证指标及当时的评分 | 只追加，不覆盖 |
| `opportunity_evidence` | 官方数据、真实买家、渠道、供应、合规及 Odoo 内部结果 | 只追加；按 `shared` 或 `project` 归属，不覆盖 |
| `opportunity_change_log` | 主档创建、更新、归档和恢复前后的快照 | 只追加，不删除 |
| `trade_data_observations` | 产品家族、地区、HS 编码、期间和贸易流向的本地观测缓存 | 只追加并按指纹去重；确认零与缺失分开保存 |
| `trade_data_refresh_requests` | 本地缓存命中、AI 补数和失败状态 | 每次补数单独留痕，不覆盖旧请求 |

公开需求、渠道、竞争、产品矩阵、供应和合规资料属于共享档案；客户联系、真实回复、RFQ、样品/试单及内部评估属于具体项目。共享资料按档案、类型、来源和标题去重，因此多个项目可以引用同一事实，不必重复调研。

项目采用软作废而不是物理删除。作废必须记录原因；“重复”或“合并”必须指向替代项目。作废会终止当前轮次及待执行任务，但保留项目历史、客户反馈、产品档案和共享证据。测试阶段清理仅限明确授权且精确识别的测试项目。

## 评分与行动

评分由 `lib/opportunity.ts` 统一计算，前端与接口不各自维护一套公式。

- 市场需求：贸易增长、买家需求证据、渠道信号；
- 客户开发：画像匹配、线索质量、复购/连带采购；
- 找货可行：供应商覆盖、单位经济、合规与物流；
- 置信度：已填写指标完整度与有效来源等级。

任一维度至少有两项信号后才显示分数；未知值保持为空，不能按 0 分处理。只有 `available` 状态的证据参与置信度，`missing` 和 `blocked` 只保留为待办记录。

系统根据三个分数分别建议：继续验证、开发画像客户、寻找产品货源、进入样品/试单或暂停观察。建议是辅助决策，不会自动修改商机阶段。

## 人工、AI 与 Odoo 的边界

所有写入接口接受统一的 `origin`：

- `user`：页面人工维护；
- `ai_assistant`：AI 补充的假设、证据或评估；
- `odoo`：CRM、询报价、销售和复购结果。

来源写入变更日志或记录的 `created_by`。AI 可以补充建议和证据，但不能绕过页面的人工阶段决策。Odoo 数据应作为 `internal` 证据写入，并使用 `internal_odoo` 来源等级；外部证据必须保留可核验的 HTTP/HTTPS 链接。

## 本地优先的贸易与销售数据

系统先按“产品家族 + 地区”读取本地贸易数据。最近一次可用观测在 120 天内时直接复用；只有缓存缺失、过期或用户明确要求强制更新时，才发送到独立的 Codex 贸易数据通道。AI 必须从官方 API、官方导出或官方页面采集，并通过受限 Bridge 增量写回，不能直接改数据库。

免费来源按用途分层：

| 来源 | 主要用途 | 边界 |
| --- | --- | --- |
| UN Comtrade | 全球年度/月度商品进出口额与数量 | 受 API 配额与商品编码粒度限制 |
| Eurostat Comext | 欧盟成员国月度/年度商品贸易 | 适合欧盟市场交叉复核 |
| U.S. Census International Trade API | 美国 HS/NAICS 月度进出口 | 免费使用通常需要 API Key |
| WTO Data / WTO API | 全球贸易、服务贸易和关税宏观序列 | 适合趋势及宏观复核，不替代商品明细 |
| World Bank WITS | 贸易、关税和发展指标 | 适合历史及关税补充，注意请求限制 |
| 各国海关与统计局 | 当地进口、出口或行业统计 | 口径、更新频率和开放格式不一致 |

贸易流量不等于终端销售额。免费官方来源主要回答“某国在某期间进口/出口了多少”，真实销售、报价、毛利和复购优先从 Odoo、平台后台或客户记录同步。Alibaba、Amazon 和 Google Trends 只作为渠道/关注度信号，不能写成贸易额或成交额。

数据状态严格区分：`available` 可以保存确认的 `0`；`missing` 必须保存空值和原因；登录、限流或访问限制使用 `blocked`。这样缺失不会在评分中被误当成零增长。

### 自动化责任边界

ChatGPT/Codex 默认负责查本地缓存、建议 HS/CN 编码、选择官方来源、采集校验、去重入库、趋势摘要和缺口提示。用户只负责三类工作：首次提供受限来源或 Odoo 的最小权限授权；产品对应多个 HS 编码时确认业务口径；决定是否联系买家、询价供应商或推进样品试单。登录、验证码、平台私有后台和第三方沟通不会由 AI 绕过或擅自执行。

渠道定义集中维护在 `lib/trade-source-catalog.ts`，商机详情与“数据来源”页面共用同一份目录，避免两处文案和自动化边界不一致。

建议的 Odoo 映射：

| Odoo 对象 | 商机中心用途 |
| --- | --- |
| CRM Lead / Opportunity | 真实买家线索、国家、画像匹配与线索质量 |
| Request for Quotation / Purchase Order | 供应商覆盖、MOQ、交期和采购价格 |
| Sale Order | 成交、销售额、毛利和渠道效果 |
| Product Template / Category | 产品家族下的可交付 SKU，不替代产品家族主数据 |
| Customer / Invoice | 复购周期、客单价和连带采购证据 |

## 生命周期

`第一轮·价值发现 → 第二轮·商业验证 → 第三轮·首单履约 → 常态开发`

任何阶段都可以进入“暂停观察”或软归档。推进阶段前建议至少具备：

1. 一条官方或可核验的地区需求证据；
2. 一条真实买家或有效客户线索证据；
3. 一条供应商报价或 Odoo 采购证据；
4. 明确的下一步行动与复核日期。

## 维护约束

- 分类主数据与项目数据分离；验证项目只能从全球画像发起，并选择同一画像、同一目标市场下相互关联的产品矩阵关系。
- 一轮可选择多条矩阵关系，默认上限为 5；创建时保存画像版本和矩阵角色、评分、证据状态及依据快照。
- 相同画像、市场、场景和渠道不得重复建立活动项目；用户必须进入原项目或把新的矩阵关系追加到原项目当前轮次。
- 产品家族档案不会因项目 Pass、归档或作废而删除；后续项目自动读取同一地区与产品家族的共享证据，项目级客户反馈仍相互隔离。
- 项目列表采用服务端搜索、状态/阶段/市场/画像/负责人/复核日期筛选和分页；轮次历史也必须分页，不能依赖一次加载全部卡片。
- 作废只改变项目及其活动轮次状态，不删除产品矩阵主数据、档案、证据或客户反馈；重复/合并必须留下替代项目链路。
- 不提供脱离全球画像的自由创建或兼容入口；项目通过轮次决策统一维护子商机与产品家族去留。
- 新增指标或来源等级时，先扩展共享类型和测试，再更新接口与页面。
- 修改评分权重时必须更新 `tests/opportunity.test.mjs`，并说明对已有商机建议的影响。
- 不物理删除评估、证据和变更日志；需要纠错时追加更正证据并说明原因。
- AI 批量写入使用相同接口和 `origin=ai_assistant`，不得直接操作数据库。
- 对接 Odoo 使用相同接口和 `origin=odoo`，按业务对象 ID 做上游幂等控制。

## API

- `GET /api/radar?view=opportunity_center`：读取验证项目、轮次、产品矩阵快照、客户反馈、子商机和证据。
- `GET /api/radar?view=opportunity_programs`：按搜索、状态、阶段、市场、画像、负责人和复核日期分页读取项目摘要。
- `GET /api/radar?view=opportunity_program_detail&programId=...`：按需读取单个项目的完整轮次、产品矩阵快照和客户反馈，避免详情依赖列表全量加载。
- `POST /api/radar` + `create_opportunity_program`：从全球画像和一组关联产品矩阵创建首轮验证项目。
- `POST /api/radar` + `add_opportunity_program_matrices`：复用已有活动项目，将尚未存在的产品矩阵加入当前轮次。
- `POST /api/radar` + `void_opportunity_program`：带原因和确认地软作废项目；重复/合并时记录替代项目。
- `POST /api/radar` + `decide_opportunity_round`：继续、调整、暂缓或淘汰项目/矩阵关系，并创建下一轮。
- `POST /api/radar` + `add_opportunity_customer_feedback`：记录第一批目标客户的真实联系与回复。
- `POST /api/radar` + `update_opportunity_program_settings`：维护双人团队分工、默认矩阵上限与复核周期。
- `POST /api/radar` + `add_opportunity_assessment`：追加评估快照。
- `POST /api/radar` + `add_opportunity_evidence`：追加证据。
- `GET /api/radar?view=trade_data_cache&opportunityId=...`：读取商机的本地贸易数据、缓存新鲜度与补数历史。
- `POST /api/radar` + `create_trade_data_request`：本地命中则直接返回；缺失或过期时创建独立补数任务。
- `POST /api/radar` + `import_trade_data`：校验来源和状态后增量写入本地观测。
- `POST /api/radar` + `fail_trade_data_request`：记录 AI 补数失败原因，避免失败被误记为零。
